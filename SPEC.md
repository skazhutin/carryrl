# carryrl: цели, требования и план

Обновлено 14 октября 2026 года. Это основная карта проекта для продолжения работы.
Правила работы — в [AGENTS.md](AGENTS.md), основания решений — в [DECISIONS.md](DECISIONS.md).

## Цель

Единый обучаемый агент осваивает широкий спектр игр, изначально тривиальные игры, игры постепенно усложняются по ходу обучения, доходя до сложных
3D-игр, по экрану и его истории. Он управляет клавиатурой и мышью, использует память,
понимает результат действий, переносит опыт и сохраняет ранее освоенные навыки.

Ближайшая цель пользователя — 100% успешных прохождений каждой из 16 атомарных игр на
отложенных уровнях, затем при изменении оформления, без лишних действий. Средний процент
по играм не заменяет этот критерий. Даже 100% конечного набора не доказывает полное
понимание всех возможных игр: нужны новые уровни, изменения механик и независимый test.

Mac ограничивает вычислительный масштаб и определяет поэтапное обучение; он не сужает
конечную цель до простых игр. Навигация и атомарные игры — учебные стенды.

## Требования

1. Основные наблюдения: RGB экрана и его история. Допускаются собственные прошлые
   команды и явное описание игры, цели и управления от пользователя.
2. Никаких скрытых координат, состояния движка, готовых маршрутов или API reward
   в основном агенте. Диагностические контроли обозначаются отдельно.
3. Единая архитектура и физические действия для разных игр. Конкретная модель и полный
   состав архитектуры выбираются сравнениями, первый кандидат не является окончательным.
4. Обучать распознавание награды по экрану: сначала видимые score/outcome, затем прогресс
   без числового счёта, исследование и полезные подцели. Не выдавать чтение HUD за
   понимание абстрактных наград неизвестной игры.
5. Промежуточные награды должны соответствовать полезным событиям. Например, открытие
   нужного инвентаря может быть этапом задачи; повторение Tab без прогресса не даёт
   бесконечную награду. Агент должен также наказываться за лишние действия.
6. Проверять историю и долгие зависимости: память после исчезновения подсказки,
   совместное управление камерой и движением, причинность, UI и цепочки действий.
7. Разные разрешения, расположение интерфейса, текстуры, темы и языки проверяются
   отдельно. Перенос на новое оформление и перенос на новую игру — разные проверки.
8. При обучении новому проверять прежние игры. Регрессия отдельных навыков не скрывается
   улучшением среднего результата.
9. Дэшборд должен явно показывать весь проект, обучение, процессы, причем не только чтобы было понятно разработчику но и просто использующему или следящему.
10. Хранение имеет ограниченный бюджет. Нужные данные и готовые признаки переиспользуются;
    холодные веса можно архивировать с проверкой полного восстановления.
11. Изучать разные метрики чтобы точно понимать и контроллировать обучение агента 

## Первый учебный набор

| Навык | ID | Задача |
| --- | --- | --- |
| Реакция | reaction | Платформа ловит движущийся мяч |
| Тайминг | timing | Flappy-like: взмах, падение, проёмы |
| Платформинг | platforming | Движение, прыжок, препятствия |
| Непрерывное управление | steering | Трасса и инерция |
| Мышь | mouse | Наведение, клик, отпускание кнопки |
| Движение и камера | camera | WASD и независимые yaw/pitch |
| Навигация | navigation | Лабиринт с видимым выходом |
| Память | memory | Исчезающая подсказка, отложенный выбор двери |
| Взаимодействие | interaction | Подойти, подобрать и использовать предмет |
| Причинность | causality | Переключатель открывает проход |
| Ключ–дверь | key_door | Найти ключ и вернуться к двери |
| Выбор цели | goal_choice | Разные выплаты и риски |
| Опасности | hazards | Ловушки и движущийся враг |
| Стрельба | shooting | Движение, прицел, огонь |
| Интерфейс | ui | Открыть меню, выбрать, подтвердить, закрыть |
| Цепочки | chain | Ключ → переключатель → дверь → выход |

Правила счёта `carryrl.atomic.efficient.v1`: в лабиринте 5/5 требует кратчайшего
допустимого пути без холостых, заблокированных и лишних команд. Успешный обход остаётся
победой со счётом 4/5. В остальных 15 задачах лишние компоненты управления исключают
5/5, а необходимые ожидания разрешены. Их глобально оптимальные траектории ещё не
определены. Победы и победы со счётом 5/5 — отдельные метрики.

## План развития

| Этап | Работа | Условие перехода |
| --- | --- | --- |
| Атомарные игры | Освоить все 16 навыков, точное управление и полезные промежуточные события | Проверяемые победы каждой игры на новых уровнях; отдельно эффективность и память |
| Визуальная награда | HUD → прогресс без score → обнаружение событий и полезных подцелей | Независимая оценка награды, устойчивость к повторам и изменению интерфейса |
| Настоящие игры Atari | Pong, Breakout, Space Invaders, Enduro, Ms. Pac-Man, Seaquest, Montezuma's Revenge | Комбинация навыков; отдельный режим награды только по видео |
| Короткие 3D-задачи | Движение, камера, поиск, предметы, бой, выход; кандидат ViZDoom | Egocentric vision, пространственная память и физическое управление |
| Minecraft | Сбор → взаимодействие → инвентарь → крафт → строительство → составные цели | Длинные цепочки, подцели и устойчивое планирование |
| Новые игры | Необученные жанры, стили, управление и механики | Раздельные zero-shot и online adaptation, измеренная эффективность опыта |
| Последовательное обучение | A → B → C с повторной проверкой A/B после каждого этапа | Сохранение политики и понимания награды в ограниченном архиве |
| Автономное освоение | Незнакомая игра, экран, универсальные действия, возможно общая инструкция | Самостоятельное обнаружение возможностей, прогресса, целей и улучшение результата |

Отдельный планировщик — идея для проверки на длинных задачах; решение о его включении
в архитектуру не принято. Долговременная память, абстрактный оценщик награды, gamepad
и полноценный мост к независимому окну игры относятся к дальнейшей реализации.
Наличие интерфейса или успешного технического smoke не считается освоением этапа.

## Как принимать результат

- До запуска фиксировать исходные веса, данные, бюджет, endpoint и протокол оценки.
- Разделять train/validation/test по уровням и смысловым конфигурациям, не по соседним кадрам.
- На текущем полном validation-наборе: 16 игр × 16 уровней = 256 эпизодов агента;
  отдельно 256 эпизодов случайной политики. Сумма 512 не означает 512 игр агента.
- Проверять успех/поражение/незавершённость по экрану, долю 5/5, лишние действия и
  показатели каждой игры; показывать видео самостоятельной игры.
- Память: обе противоположные подсказки для каждой геометрии, первый выбор и пары,
  отдельно обычный режим и нейтральное ожидание.
- Оформление проверять при неизменных механике, уровнях и языке, меняя только изображение
  и HUD. Размер среды 64/96/128 проверять отдельно: он может менять механику, а не только
  картинку. Язык RU/EN — отдельная проверка. Эти результаты не смешивать с основной кривой;
  переводы одной инструкции не доказывают понимание произвольного текста.
- Политика, оценщик и optimizer заморожены в оценке; рабочая память обновляется внутри
  эпизода и сбрасывается между эпизодами. Адаптация оценивается отдельно.
- Сравнивать одинаковые банки, сложность, scoring_version, инструкции и sampling.
  Не ранжировать результаты разных наборов одним числом. Test сохранять для независимой
  оценки после выбора модели; многократно используемый validation является разработочным.
- При регрессии сохранять проверенную исходную модель. Loss, успех учителя и сумма
  предсказанных наград не заменяют успех самостоятельной игры.

## Проверенное состояние на 13.10.2026

Все прогоны остановлены по просьбе пользователя; активного обучения нет.
Следующий эксперимент подготовлен в коде, но не запускался.

| Проверка на одинаковом наборе | Исходная модель | Новое обучение на оформленных ошибках |
| --- | --- | --- |
| Победы, 256 эпизодов | 155 (60.55%) | 143 (55.86%) |
| Победы со счётом 5/5 | 132 | 123 |
| Лабиринт: победы / кратчайшие прохождения | 10 / 6 из 16 | 10 / 7 из 16 |
| Память: первый выбор, оба режима | 32/32 в каждом | 32/32 в каждом |
| Память: обе версии пары, оба режима | 16/16 в каждом | 16/16 в каждом |
| Смешанная диагностика оформления, размеров среды и RU/EN; 6 × 32 эпизода | 44/192 | 55/192 |

Случайная политика на основном наборе: 13/256 побед. Полный граф и новые данные
работают, но освоение всех игр и 100% не достигнуты. На основном сопоставимом наборе
новая модель выигрывает реже; её не принимаем как основную.
Особенно слабы камера, взаимодействие, причинность и короткие цепочки.

Сумма 44/192 → 55/192 относится к смешанной диагностике: одновременно различаются
оформление, размер среды и язык. Выборки допускают повторы уровней, а размер среды
может менять механику. Поэтому рост этой суммы не доказывает отдельно устойчивость
к оформлению, понимание текста или перенос на новые игры. Сравнения двух моделей
внутри одинаковых условий остаются полезными; условия нужно показывать раздельно.

Это результаты одной пары обученных моделей на используемом для разработки validation.
Повторные оценки тех же весов не заменяют независимые обучения и финальный test.
Причина регрессии пока не установлена: улучшение loss, успех программного учителя
и рабочий процесс обучения не доказывают улучшение самостоятельной игры агента.

## Ближайшие шаги после возобновления

1. Довести удобство дэшборда: обычный выбор должен показывать понятные сравниваемые
   модели, дату, результат и вывод. Старые несопоставимые проверки — отдельный архив.
   Переключение записи не должно скрывать реальный ход другого активного обучения.
2. Перед запуском проверить загрузку готового корпуса и переиспользование признаков;
   зафиксировать условия оценки, бюджет, момент окончания обучения и критерий выбора
   модели. Раздельно оценивать обычные уровни, оформление, размер среды и язык.
3. Проверить гипотезу сохранения навыков: начать с исходной модели 155/256, использовать
   тот же корпус, меньший learning rate `1e-5`, восемь эпох и optional
   `--canonical-anchor-coefficient 1`. Код и численная Torch/MLX-парность проверены;
   практическая польза пока неизвестна. Это совместная смена режима обучения, не
   изолированное доказательство эффекта KL.
4. Сохранить промежуточные веса, проверить тот же полный набор,
   память и оформление. Если выигрыша без потери навыков нет, разобрать ошибки по играм
   и сравнить следующий подход; не повторять короткие прогоны без проверяемой гипотезы.
5. Уточнить эффективность действий для каждой механики и добиться целевого результата
   по каждой игре, затем подтвердить его новым независимым набором.
6. Продолжать архитектурные сравнения и переход к следующей ступени только по результатам.

Настройка локальной среды и команды находятся в `AGENTS.md`. Свежий Git checkout
содержит код и протоколы, но не автоматически обученные веса и многогигабайтные данные.
