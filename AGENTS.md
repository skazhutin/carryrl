# Работа над carryrl

## Контекст

Документация проекта состоит только из трёх файлов в корне:

- `SPEC.md`: цели, требования, этапы, критерии успеха и проверенное состояние.
- `DECISIONS.md`: принятые решения, временные инженерные выборы и их основания.
- `AGENTS.md`: правила работы и команды.

Не создавай дополнительные README, планы, отчёты или handoff-файлы в документации
репозитория. Обновляй соответствующий существующий файл. Временные логи и технические
заметки оставляй в `.cache/` или вне репозитория. Результаты экспериментов — в `runs/`.

## Работа с пользователем и кодом

- Отвечай по-русски, кратко и конкретно. Начинай с результата или существенного вывода.
- Выполняй разрешённую работу до проверяемого результата; рутинные обратимые решения
  принимай самостоятельно. Уточняй только существенную неопределённость, потерю данных,
  расходы или внешние обязательства. Учитывай уже данное разрешение.
- Перед изменениями проверь Git status и существующую реализацию. Сохраняй чужие изменения.
- Используй `rg` для поиска; читай нужные участки, не весь репозиторий или большие логи.
- Исправляй причину проблемы, соблюдай существующую архитектуру и зависимости.
  Избегай посторонних рефакторингов, массового форматирования и обновлений пакетов.
- Для независимых нетривиальных задач используй сабагентов с ограниченной областью. Один автор на изменяемую область.
- Проверяй существенные утверждения по исходникам и результатам. Отделяй требования,
  решения пользователя, наблюдения и предложения. Не превращай гипотезу в требование.
- Не публикуй секреты, веса, кеши и большие данные в Git. Не удаляй данные на основании
  предположения, что они больше не нужны: проверь ссылки и возможность восстановления.
- Не запускай длительное обучение автоматически при открытии проекта.

## Границы ML

- Основная политика получает RGB, историю собственных действий и опционально явный текст.
  Скрытое состояние игры, её API reward и ответы контроллера не являются входом политики.
- Учитель и диагностические контроллеры не выдаются за обученного агента.
- Сохраняй реально исполненную историю команд; целевые действия учителя хранятся отдельно.
- Разделяй train, validation и test до сбора данных; исключай смысловые совпадения уровней
  между банками. Test используется после выбора и заморозки модели.
- Сравнивай одинаковые версии игр, правил счёта, уровни, инструкции и режимы оценки.
  Повторение обучающих действий, сумма наград и снижение loss не доказывают побед.
- Показывай качество каждой игры, сохранение навыков, память и другое оформление отдельно.
  Не объявляй 100% проверочного набора доказательством понимания любых неизвестных игр.
- Учитывай общий бюджет RAM Mac, реальные байты на диске, кеши и промежуточные снимки.
  Проверяй завершение процесса и существование checkpoint, а не только старый status.json.

## Среда и команды

Python 3.12, пакетный менеджер `uv`, исходники в `src/carryrl`, тесты в `tests`.
Для текущего Mac доступны PyTorch CPU/MPS и дополнительный MLX/Metal.

```sh
uv sync --locked --extra mlx --extra monitor
uv run --locked pytest -q
uv run --locked ruff check src scripts tests
node --test tests/frontend/overview.test.cjs
```

Интерфейс и ручные игры запускаются отдельно от обучения:

```sh
uv run --locked python -m carryrl.dashboard.overview --runs runs --registry .cache/active_mlx_launch.json --port 6009
uv run --locked python -m carryrl.play --port 6007
```

Параметры обучения и обратимого архивирования:

```sh
uv run --locked --extra mlx --extra monitor python scripts/train_imitation.py --help
uv run --locked python scripts/manage_run_storage.py --help
```

консоль и сохранение воспроизведения при обновлении. После проверок осмотри итоговые
изменения и новые файлы. В ответе укажи результат, проверку и существенные ограничения.
